## 1. Контекст проекта

### 1.1 Предмет исследования
	•	Описание проблемы/вызова, который пытаемся решить (например: ускорение работы текущего решения, повышение метрик и качества).
	•	Почему возникла идея это протестировать?
	•	Каковы критерии успеха с точки зрения исследования.

Большинство современных ретриверов с архитектурой bi-encoder плохо понимают явные инструкции в запросе (например, "нужна именно научная статья, а не новость"). Есть альтернатива в виде переранжирования через cross-encorder'ы, но это долго и дорого

Идея: Проверить подход из статьи Promptriever, где bi-encoder обучается с учетом инструкций
Цель: Обучить bi-encoder, который сразу учитывает инструкцию, отсеивая релевантные по теме, но не подходящие по инструкции документы
Критерии успеха:
- Повышение качества на запросах с инструкциями по метрикам ранжирования и instruction-following
- Нет значимой просадки на запросах без инструкций
- В аблейшенах увидим, что instruction negatives вносят вклад

### 1.2 Ограничения и допущения
	•	Что нельзя/не будет делать (например: не интегрируемся с X, не обрабатываем Y).
	•	Предположения о данных, инфраструктуре, требованиях к безопасности, к нормативам.

Ресурсы: ограниченные вычислительные мощности для обучения/генерации синтетики. Обучение ретривера с инитом из LLM пока под вопросом, поэтому, возможно, придется сфокусироваться на меньших моделях (небольшие encoder-only модели).
Данные: планирую использовать mMARCO. Перевод там автоматический, поэтому допускаем наличие шума в текстах. И, опять же, все данные взять не получится из-за ограниченных мощностей.
Язык: в рамках исследования работаем только с русским языком

## 2. Архитектура решения

### 2.1 Общая схема
	•	Скорее всего архитектура существующего решения и/или её доработки

Оффлайн часть:
- Беру mMARCO (ru подсемпл), семплирую оттуда 25–50k запросов
- Из датасета собираю обучающие примеры вида:
  - query, positive_passage, hard_negative_passage
  - instruction + query, positive_passage (возможно, сгенерированный, если инструкция поломала релевантность), instruction negative
- Генериую инструкции через LLM (скорее через небольшие локальные, надеюсь на 8B)
- Дообучаю bi-encoder с contrastive loss
- Собираю golden set (ручной/полуручной) для финальной оценки

Онлайн часть:
- Получаем вход вида “инструкция (опционально) + запрос”
- Через обученный ретривер получаем эмбеддинг.
- Поиск ANN через Qdrant релевантных чанков (надо будет подумать, какие документы кладем в Базу Данных)
- На выход: список релевантных документов/чанков для запроса с инструкцией
- Опционально: генератор, отвечающий на вопрос пользователя

### 2.2 Какие гипотезы тестируем?
	•	Начинаем с меньшего и самого простого, заканчиваем самыми трудоёмкими решениями;

1. Если обучать ретривер на примерах вида ‘instruction + query’, то на запросах с инструкциями качество IR вырастет (модель начнет лучше учитывать инструкции)
2. Добавление instruction negatives даёт отдельный значимый вклад
3. Можно добиться улучшения на instruction-запросах без заметной деградации на обычных запросах (без инструкций)
4. Дообучение на mMARCO с синтетическими инструкциями улучшит поведение на golden set, но на внешних русских IR бенчмарках эффект будет более слабым

## 3. Данные и качество знаний

Как много данных можно найти в теории? Какого рода эти данные (предметная область? либо если это general knowledge, то надо аргументировать разнообразие)

### 3.1 Сбор и предобработка данных
	•	Источники документов/текста, форматы (PDF, HTML, TXT, базы данных).
	•	Шаги предобработки: токенизация, очистка, выделение сущностей, сегментация.
	•	Метаданные: добавление тегов, категоризация, дата, автор.


#### Сбор данных
- Источник данных для обучения ретривера: ru часть mMARCO (структура максимально близка к тому, что было в статье)  
- Ориентировачно 25–50k запросов на train, на val 1-2k 
- Формат исходных данных: query, positive_passage, hard_negative_passage
- Что нужно добавить синтетически: instruction, positive_passage (возможно, сгенерированный, если инструкция поломала релевантность), instruction negative

#### Предобработка текстов:
- чистка пустых строк, возможно битых (мб где-то кодировка полетела и т.д.)
- фильтрация текстов на не русском языке (при наличии)
- дедупликация
- возможно, ограничение по длине (вдруг модель перевода зациклилась и нагенерила 20к токенов) 
- чанкинг, скорее всего, не нужен (в датасете он уже произведен)


#### Метаданные
- query_id
- passage_id
- has_instruction
- длина текстов (символы/слова/токены)

### 3.2 Метрики качества знаний
	•	Покрытие: % документов в базе относящихся к сценариям.
	•	Актуальность: как быстро база обновляется, как отражаются изменения.
	•	Консистентность: нет дубликатов, нет противоречивых данных.
	•	Проверка: ручная ревизия, спотыкаемые примеры.


- Валидация синтетики: нужно проверить, что сгенерированные инструкции и instruction negatives вообще имеют смысл. Надо посмотреть глазами, при необходимости продумать способы фильтрации (например, через LLM или слишком высокую неопределенность/несогласованность бейзлайновых моделей)
- Длина текстов: Проверить распределение длин. Слишком длинные/короткие можно выкинуть, чтобы не поломать обучение
- Языковая проверка: проверяем и фильтруем через готовые библиотеки (например, langdetect)/легкие модели
- Проверка на дубли по query_id и passage_id

## 4. Модель

### 4.1 Выбор модели
	•	Указание модели: объяснение, почему выбранa.
	•	Ограничения: скорость работы, размер контекста.

В качестве базы планирую взять DeepPavlov/rubert-base-cased и intfloat/multilingual-e5-base:
1. Хорошая работа с русским языком (особенно у первой модели)
2. Небольшой размер (=> высокая скорость обучения/инференса, ниже требования по VRAM)
3. Вторая модель уже прошла стадию обучения через contrastive loss, так что меньше шанс развала

Ограничения: 
- длина в 512 токенов, но для нашей задачи должно хватить
- LLM уже умеют следовать инструкциям, с encoder-only может быть посложнее

### 4.2 Контроль качества выполнения
	•	Метрики: точность, полнота/coverage, полезность, удовлетворённость пользователя.
	•	Оценка ошибок.

Основные метрики стандартные: MAP, MRR, nDCG. Но еще потребуется специфичная для задачи —  p-MRR.

### 4.3 Обучение/дообучение
	•	Если предусмотрено fine-tuning или RLHF: данные, процесс, метрики.
	•	Версионирование моделей, rollback план.

Процесс обучения:
- Contrastive Loss
- Баланс hard/instruction negatives, запросов с/без инструкций при сборе троек для обучения
- Метрики перечислены выше
